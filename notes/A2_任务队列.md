## 队列的三点价值

1. **缓存**：worker 都在忙的时候，新来的任务得有个地方待着，不能丢。
2. **解耦（交接）**：提交方把任务放进队列就走，不用等 worker 干完。提交和执行在时间上拆开了。
3. **资源有界 / 背压**：线程数由配置决定，不跟着流量走。没有队列，流量高峰就得靠「来一个任务开一个线程」扛，线程数会失控 —— 也就是我一开始说的「无法控制人数、招不过来」。有了队列，高峰只是把队列撑长，线程数不动。

## 竞态：lost update（丢失更新）

两个提交方 A、B 同时往队尾放任务，都先读到「下一个写入位置 idx = 0」，然后都往 idx 0 写，写完后 next 应该变成 2 却只变成 1。后写的覆盖先写的，一个任务凭空消失。

更糟的一种情况：队列只剩 1 个空位时，A、B 都读到「还有 1 个空位」，都认为自己能放进去，结果 B 拿到的是一个**空行**（读到的位置根本没数据）。

关键点是：**「检查还有没有位置」和「占用这个位置」必须是不可分割的一步。** 中间只要能被另一个线程插进来，状态就错了。这不是「概率很小」，是必然会发生的错误。

## 为什么是 `Arc<Mutex<T>>`，两个都不能少

- 只有 `Arc`，没有 `Mutex`：多个线程能同时拿到数据，但 `Arc` 只给共享引用 `&T`，拿不到 `&mut T`，改不动队列。而且即使能改，多个线程同时改还是上面那个 lost update。**编译期就过不去**（拿不到可变引用）。
- 只有 `Mutex`，没有 `Arc`：`Mutex` 解决了互斥，但解决不了所有权和生命周期 —— 线程闭包要求 `'static`，借来的引用活不了那么久，每个线程都得自己持有一份所有权。**也是编译期错误。**

所以两个必须成对出现：`Arc` 管**所有权和生命周期**（让多个线程各自持有一份），`Mutex` 管**互斥**（同一时刻只有一个能改）。

Rust 在这里的好处是：缺任何一个都不是「跑起来偶发出错」，而是**编译不过**。错误被提前到了编译期。

## 这环我卡在哪

- 总结时漏了队列的第三点价值（资源有界 / 背压）。缓存和解耦比较直觉，背压那一点容易忘，但它恰恰是「为什么不能靠无限开线程解决」的答案。

``` rust
fn run(shared: Arc<Shared>) {
    loop {
        // TODO(你・留白 A)：等任务 + 取任务 + 判断退出
        //
        // 要满足五条：
        //   1. 抢 shared.inner 的锁
        //   2. 没任务 且 没关闭 → 睡（shared.wake.wait，记得放 while 里）
        //   3. 醒了发现「已关闭 且 队列空」→ return
        //   4. 否则 pop_front 一个任务
        //   5. 先出锁，再跑任务 —— 拿着锁跑任务会把所有提交方堵死

        let job = {
            // 1. 抢 shared.inner 的锁
            let mut inner = shared.inner.lock().unwrap(); 
            // 2. 没任务 且 没关闭 → 睡（shared.wake.wait，记得放 while 里）
            while inner.jobs.is_empty() && !inner.is_shutdown {  
                inner = shared.wake.wait(inner).unwrap();
            }

            // 3. 醒了发现「已关闭 且 队列空」→ return
            if inner.is_shutdown && inner.jobs.is_empty() {
                return;
            };
            // 4. 否则 pop_front 一个任务
            inner.jobs.pop_front().unwrap()
        };
        job();
    }
}
```

`pop_front().unwrap()` 这个 unwrap 为什么安全？
因为它依赖一条不写在任何一行的规则 —— 「走到这一行时，队列必非空」这条规则由上面两处代码（while 条件 + 退出分支）共同撑起。它现在是对的，但脆弱：以后谁改动 while 条件、忘了同步改退出分支，这个 unwrap 就会炸，而且炸的时候报错信息完全不会指向真正的凶手。留个心眼：依赖非局部不变量的 unwrap，要么加注释说明前提，要么改成显式 match。现在不动它，记住这个感觉就行。
