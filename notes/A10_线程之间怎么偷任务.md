# A10：线程之间怎么偷任务？

## 1. 为什么需要 work stealing？

如果每个 worker 只有自己的私有队列，那么很容易出现负载不均衡：

```text
worker 0：私有队列 [A B C D E F ...]，忙得很
worker 1：空
worker 2：空
worker 3：空
```

如果空闲 worker 只等待全局队列：

```text
全局队列：空
```

那么 worker 1/2/3 会一直闲着。

问题是：

> 系统明明还有大量工作，但工作被堆在某个忙 worker 的私有队列里。

所以 idle worker 不能只等新任务主动送来，还必须能够：

> 去其他 worker 的私有队列里偷任务。

这就是 **work stealing**。

---

## 2. 为什么 owner 和 thief 从不同方向拿任务？

使用一个双端队列 deque：

```text
top                                      bottom
 ↓                                          ↓
[ 老任务 ][ ................. ][ 新任务 ]
```

约定：

```text
owner：
push bottom
pop  bottom

thief：
steal top
```

也就是：

> owner 吃最新任务，thief 偷最老任务。

---

## 3. 为什么 thief 偷最老的一端？

偷任务不是免费的。

一次 steal 可能涉及：

* 跨核访问；
* 原子操作；
* CAS；
* cache coherence；
* cache line 在 CPU 核之间迁移。

所以：

> 偷一次最好偷到一个“够肥”的任务。

在 fork-join / 递归任务中，较老的任务通常更靠近递归树的上层。

例如：

```text
solve(1000)
├── solve(500)
│   ├── solve(250)
│   └── ...
└── solve(500)
```

越老的任务通常代表：

```text
更大的子问题
→ 更大的子树
→ 后续还能继续产生更多任务
```

因此 thief 从 top 偷老任务：

```text
偷一次
↓
获得一大块工作
↓
自己可以忙较长时间
```

比偷一个很小的叶子任务更划算。

---

## 4. 为什么 owner 从最新的一端 push/pop？

owner 使用 bottom：

```text
push_bottom
pop_bottom
```

形成 LIFO 行为。

这样有两个主要好处。

## 4.1 缓存局部性

刚产生的任务往往与当前任务访问相近的数据。

例如：

```text
处理节点 A
↓
生成 A.left / A.right
```

刚刚访问过的数据可能仍然位于：

```text
L1 / L2 cache
```

owner 马上执行最新任务，有较好的时间局部性。

---

## 4.2 递归工作集更小

LIFO 更接近 DFS：

```text
不断深入一条递归分支
```

相比 BFS 同时保留整层任务：

```text
2
4
8
16
32
...
```

DFS 通常让同时存活的任务更少。

因此：

> owner 在 bottom 端工作，有助于控制内存工作集。

---

## 5. 两端分工还顺带减少竞争

如果 owner 和 thief 都操作同一端：

```text
owner ──┐
        ├── 同一个索引 / cache line
thief ──┘
```

会产生更多：

```text
CAS 冲突
cache line ping-pong
同步开销
```

而现在：

```text
top                               bottom
 ↑                                    ↑
thief                              owner
```

绝大多数时候双方互不干扰。

真正必须竞争的只有一个场景：

> 队列只剩最后一个任务。

---

## 6. 数据模型：环形缓冲区

假设容量固定为：

```rust
const CAP: usize = 1024;
```

逻辑下标 `top`、`bottom` 可以不断增长：

```text
0, 1, 2, ... 1023, 1024, 1025 ...
```

映射到实际槽位：

```rust
slot = index % CAP;
```

如果容量是 2 的幂：

```rust
slot = index & (CAP - 1);
```

例如：

```text
1023 → slot[1023]
1024 → slot[0]
1025 → slot[1]
```

所以物理数组会不断循环使用，称为**环形缓冲区**。

---

## 7. 队列的不变量

逻辑队列表示为半开区间：

```text
[top, bottom)
```

例如：

```text
top = 5
bottom = 8
```

实际元素是：

```text
5, 6, 7
```

不包含 8。

因此：

```text
队列长度 = bottom - top
```

空队列：

```text
top == bottom
```

---

## 8. 三个核心对象，谁读谁写？

| 对象          | 谁写              | 谁读              | 特征       |
| ----------- | --------------- | --------------- | -------- |
| `bottom`    | owner           | owner + thieves | 单写者      |
| `top`       | owner + thieves | owner + thieves | 多写者      |
| `buffer[i]` | owner           | 获胜的 owner/thief | 单写，多线程读取 |

这张表是后面同步推理的地基。

---

## 9. `bottom`：owner 的私账

只有 owner 能写：

```text
bottom
```

所以 owner 可以直接：

```text
bottom -= 1
bottom += 1
```

不需要和 thief CAS 竞争 `bottom`。

因此：

> bottom 是 owner 的私账，可以先改后验。

---

## 10. `top`：所有竞争者的公账

多个 thief 都可能试图偷：

```text
slot[top]
```

如果直接：

```rust
top += 1;
```

两个 thief 可能同时看到：

```text
top = 10
```

然后：

```text
thief A：拿任务 10
thief B：也拿任务 10
```

同一个任务执行两次。

因此必须通过 CAS：

```text
CAS(top, 10, 11)
```

只能有一个线程成功。

所以：

> top 是公账，必须通过原子仲裁才能改。

---

## 11. CAS 抢的不是槽，而是消费权

例如：

```text
top = 12
```

两个 thief：

```text
A：CAS 12 → 13
B：CAS 12 → 13
```

只能一个成功。

成功代表：

> “逻辑下标 12 的唯一消费权归我。”

因此真正被抢的是：

```text
逻辑下标的所有权
```

不是：

```text
某一块物理内存本身
```

尤其因为环形缓冲会复用槽位：

```text
逻辑 12
逻辑 1036
```

甚至可能映射到同一个物理槽。

所以协议必须围绕**逻辑下标**建立。

---

## 12. push：先放货，再挂牌

owner push：

```text
1. 写 slot[bottom & mask]
2. 发布新的 bottom
```

必须是这个顺序。

例如：

```text
slot[5] = job
bottom = 6
```

含义：

> 先把货真正放进槽，再告诉别人“现在这里有任务”。

如果顺序反过来：

```text
bottom = 6
slot[5] = job
```

thief 可能：

```text
看到 bottom = 6
↓
判断有任务
↓
读取 slot[5]
↓
但 owner 还没把 job 写完
```

所以：

> bottom 的增长承担了“任务已经可见”的发布含义。

---

## 13. pop：owner 从自己的端拿

owner pop 的核心流程：

```text
1. b = bottom - 1
2. bottom = b
3. 栅栏 / 同步
4. t = top
5. 根据 b 与 t 的关系判断
```

有三种局面。

---

## 13.1 `b < t`：其实已经空了

说明 owner 先斩的那一步过头了：

```text
bottom 已经缩到 top 左边
```

所以需要：

```text
bottom = top
```

回滚成空队列状态。

然后：

```text
return None
```

---

## 13.2 `b > t`：owner 稳赢

owner 要拿：

```text
slot[b]
```

而 thief 永远从：

```text
slot[t]
```

偷。

当：

```text
b > t
```

两者不是同一个逻辑下标。

例如：

```text
top = 5
b   = 7
```

thief：

```text
目标 = 5
```

owner：

```text
目标 = 7
```

所以双方可以同时成功。

---

## 14. 为什么只有最后一个任务才需要打架？

owner 瞄准：

```text
bottom - 1
```

thief 瞄准：

```text
top
```

两者相等时：

```text
bottom - 1 == top
```

也就是：

```text
bottom == top + 1
```

队列刚好只剩一个元素。

例如：

```text
[top, bottom) = [5, 6)
```

唯一任务：

```text
slot[5]
```

此时：

```text
owner 想拿 5
thief 也想拿 5
```

必须有唯一裁决。

---

## 15. 最后一个任务：owner 也要竞争 top

owner 先：

```text
bottom -= 1
```

于是：

```text
bottom == top
```

表示自己预约的正是最后一个任务。

此时 owner 不能直接宣布胜利。

必须：

```text
CAS(top, top, top + 1)
```

和 thief 竞争。

成功：

```text
最后一个任务归 owner
```

失败：

```text
说明 thief 已经推进了 top
→ 最后一个任务归 thief
```

---

## 16. 为什么 owner 输了要回滚？

因为 owner 一开始已经修改过自己的：

```text
bottom
```

它采用的是：

> 先改私账，再验证。

如果最后 CAS 输了，说明任务已经被 thief 拿走。

owner 必须修正自己的边界：

```text
bottom = top
```

恢复成正确的空队列状态。

---

## 17. 为什么 thief 输了 CAS 不需要回滚？

thief 的流程是：

```text
读取 top = t
↓
CAS(t → t+1)
```

只有 CAS 成功时，`top` 才真的被它修改。

失败意味着：

```text
我什么都没改
```

因此直接重试即可。

所以形成一个非常漂亮的不对称：

```text
owner：
bottom 是私账
→ 先改后验
→ 输了需要回滚

thief：
top 是公账
→ 先 CAS，成功才改
→ 输了无需回滚
```

---

## 18. steal：从 top 抢逻辑下标

简化流程：

```text
1. t = load(top)
2. fence / 同步
3. b = load(bottom)

4. 如果 t >= b
      → 队列空
      → None

5. CAS top: t → t+1
      成功 → 获得逻辑下标 t
      失败 → 重试
```

重点：

```text
CAS 成功
```

之后，thief 才拥有读取：

```text
slot[t]
```

的资格。

---

## 19. 为什么需要栅栏？

原子操作不等于：

> 所有线程都立即按同一个顺序看见所有变量。

`top` 和 `bottom` 是两个不同的原子变量。

CPU / 编译器可能：

* 延迟某个写的可见性；
* 重新排序某些独立内存操作；
* 让另一个核暂时读到旧值。

危险场景是：

```text
owner 没看到 thief 已经推进 top
同时
thief 没看到 owner 已经缩小 bottom
```

于是双方都认为：

```text
任务归我
```

对于最后一个任务，这会导致双重消费。

---

## 20. SeqCst 栅栏买到的是什么？

它不是简单保证：

> 所有 load 永远读最新值。

真正需要的是：

> 对关键竞争操作建立一个全局一致的顺序，使 owner 和 thief 不可能双方都基于旧世界宣布胜利。

也就是至少发生一种：

```text
thief 看见新的 bottom
→ 知道任务已经没了
→ 放弃
```

或者：

```text
owner 看见新的 top
→ 知道 thief 已经赢了
→ 回滚
```

不要求双方都看见对方。

只要求：

> 至少有一方必须看到足以打破“双赢”的状态。

---

## 21. `bottom` 和 `top` 在协议中的角色不同

可以这样记：

```text
bottom → publication
top    → arbitration
slot   → payload
```

中文：

```text
bottom：有没有货
top：货归谁
slot：真正的货
```

---

## 22. 为什么 bottom 比 top 简单？

`bottom`：

```text
只有 owner 写
```

所以没有：

```text
两个写者同时推进 bottom
```

的写写竞争。

因此通常不需要 CAS。

但要注意：

> 单写者只说明“不需要竞争写权限”，不代表所有访问天然都可以无脑使用 Relaxed。

因为 push 中：

```text
写 slot
↓
更新 bottom
```

还承担着数据发布职责。

具体的 Release / Acquire / fence 如何放，要看采用的 Chase-Lev 实现版本。

---

## 23. top 为什么是核心裁决变量？

因为每次：

```text
top: t → t+1
```

都代表：

> 逻辑任务 t 已经有唯一消费者了。

多个 thief 会修改 top。

最后一个任务竞争时，owner 也会修改 top。

所以：

```text
top
```

不是简单的队列长度信息，而是：

> 消费所有权的裁决点。

---

## 24. 为什么槽本身可以不是原子？

> 2026-09-19 注：实现的槽已经从 `UnsafeCell<MaybeUninit<Job>>` 换成 `AtomicPtr<T>`（指针间接层，见第 26 节）。这一节讲的两层保证依然成立，只是「读槽」退化成「读一个地址」。

槽可以类似：

```rust
UnsafeCell<MaybeUninit<Job>>
```

owner 普通写：

```text
slot[i] = job
```

消费者普通读。

之所以安全，不是因为 `UnsafeCell` 有同步能力。

它没有。

安全来自两套协议。

---

## 24.1 第一层：保证“货已经写完”

owner：

```text
写 slot
↓
发布任务存在
```

消费者必须在同步链建立之后才能读。

目的是形成：

```text
owner 对 slot 的写
        happens-before
消费者对 slot 的读
```

避免读到未初始化/半初始化的数据。

---

## 24.2 第二层：保证“只有一个人拿货”

即使数据已经完整可见，也不能让两个消费者都拿同一个任务。

因此：

```text
CAS(top)
```

负责：

> 唯一消费权。

所以两套机制分别解决：

```text
发布同步：
数据写完了吗？

top CAS：
数据归谁？
```

不能混为一谈。

---

## 25. `UnsafeCell` 到底负责什么？

`UnsafeCell` 只是在告诉 Rust：

> 即使从共享引用出发，我也要允许内部发生可变访问。

它不会提供：

* 原子性；
* 内存序；
* happens-before；
* 唯一消费者；
* 锁；
* 数据竞争保护。

所以：

```text
UnsafeCell
    ↓
允许写底层代码

Chase-Lev 协议
+ 原子操作
+ 内存序
+ CAS
    ↓
证明代码安全
```

这就是无锁 Rust 的典型分工：

> 编译器允许你绕开部分静态借用规则，但你必须自己证明并发协议不会制造 data race。

---

## 26. 指针间接层：读地址挪到 CAS 之后，可见性靠三层担保

槽里放的不是 T 本身，而是堆上那件货的地址：

```text
push：slot[i] = Box::into_raw(Box::new(value))
取货：Box::from_raw(slot[i])   —— 只在赢了 CAS 之后
```

于是「读槽」退化成「读一个地址」：值拷贝，不涉及所有权，赢或输都没有 drop 要管。
steal 里的读地址因此可以挪到 CAS 成功之后再发生。

但问题还在：

> 赢了 CAS 之后才去读地址，凭什么保证「堆上那件货一定看得见」？

答案是三层，缺一不可。

> 别和上一节的两层混成一套编号：上一节切的是「发布 vs 唯一性」两件不同的事，这三层全落在发布这一侧。

### 第一层：地址值是对的（读到的是 ptr_t，不是上个纪元的幽灵地址）

CAS 赢 ⟹ 真实 top 曾 == t ⟹ 容量检查的逆否命题（复用该物理槽需要 top > t）⟹ 这个槽自 store(ptr_t) 之后从未被复写——modification order 的最新值就是 ptr_t。

这层由「CAS 闸门 + 容量检查」共同担保，也就是 arbitration 顺便解决了 lifetime。

### 第二层：货本身写得完（Box 里 T 的字段全部可见）

靠 steal 开头那步 `bottom.load(Acquire)`。它读到的某个 b' > t，写出 b' 的动作是 owner push 里的 `bottom.store(b', Release)`，于是 synchronizes-with 成立：owner 在那之前的所有动作——构造 T、`Box::into_raw`、`slot.store(ptr_t)`——全部 happens-before CAS 之后的 `load_ptr` 和 `from_raw`。

这是 publication 层的接收端，和 Q4b 修正过的那条链是同一条。

### 第三层：一个角落的封口——bottom 读到的是回滚值怎么办？

回滚是 Relaxed 存的，不建立同步。但两种回滚（`==` 案例写 t+1、扑空案例写 b）都只发生在「真实 top 已经越过该值」之后——所以读到回滚值的 thief 手里的 top 必然过期，CAS 必输，永远走不到解引用。

结论：

> 赢家必有链条。

---

## 27. 对称性：可见性论证只属于 thief

pop 完全不需要这套论证——owner 拿的货是它自己 push 的，同线程、程序序、天然有序。

可见性问题只在 steal 存在，因为只有 thief 跨线程。

> 三个角色里，publication 的接收端只有一个客户。

---

## 28. 整个 work-stealing deque 的核心图

```text
                  Chase-Lev deque

top                                      bottom
 ↓                                          ↓
[ 老 / 大任务 ][ ............... ][ 新 / 小任务 ]
 ↑                                          ↑
thief                                     owner
steal                                     push/pop
```

绝大多数时候：

```text
owner 操作 bottom
thief 操作 top
```

互不冲突。

只有：

```text
只剩最后一个任务
```

时：

```text
owner
   \
    → CAS(top) ← thief
```

由 top 仲裁唯一赢家。

---

## 29. 最重要的两句话

第一句：

> **bottom 是私账，可以先改后验；top 是公账，必须 CAS。**

第二句：

> **抢的不是内存槽，而是逻辑下标的唯一消费权。**

再补一条整体模型：

> **bottom 管“有没有货”，top 管“货归谁”，slot 才是真正的货。**

这三句话基本就是 Chase-Lev work stealing 的骨架。

## 这环我卡在哪

- **快照事故**：先按经典写法让槽是 `UnsafeCell<MaybeUninit<T>>`，steal 里用 `ptr::read` 抄一份快照再 CAS。快照是位级复制，等于凭空多出一份所有权，赢 / 输两条路上的 drop 都得自己盯——这一环最先绊住的就是这里。
- **指针间接层**：槽改成 `AtomicPtr<T>`（`Box::into_raw` 存、`Box::from_raw` 取），「读槽」退化成读一个地址，快照那套 drop 顾虑整块消失。
- **环复用定理**：地址即使读得早，也不会是「上个纪元的幽灵地址」——复写同一个物理槽要求 top 已经越过该逻辑下标（容量检查的逆否命题），这正是第 26 节第一层的来源。
