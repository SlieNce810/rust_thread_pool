① T: Send + 'static——今天最重要的一个「为什么」
你收到的那个编译错误，编译器把整条证据链都摆出来了，值得逐环读：


wrapped 闭包要变成 Job（Box<dyn FnOnce() + Send>）→ 闭包必须 Send
 └ 闭包捕获了 tx: Sender<T>            → Sender<T> 必须 Send
    └ Sender 里是 Arc<Inner<T>>        → Arc<Inner<T>> 必须 Send
       └ Inner 里是 Mutex<Slot<T>>     → Inner<T> 必须 Send
          └ Slot 的 Filled(T) 里装着 T  → **T 必须 Send**
所以 T: Send 不是仪式性的 bound，是编译器在要求你出示证明：「这个 T 类型的值，将随闭包被押运到另一个线程，它凭什么安全？」——Arc/Mutex 都不生产安全性，它们只是把要求传导到最后一环：你的 T。'static 同理（Job 要求闭包活多久，T 就得活多久）。这是 Rust 自动 trait 系统的精髓：安全性要求会沿着类型结构自动传播，最后落在你头上的，恰好就是你真正需要担保的那件事。

② Box::new(job) → Box::new(wrapped)——你的真 bug
你把包好的闭包造出来了，压进队列的却是原始 job。后果链条：worker 执行原始 job → 它只会算出结果然后丢弃 → tx.send 永远不发生 → 槽永远 Empty → wait() 挂死。这是并发编程里最阴的一类 bug：不报错，只是永远等。如果测试没写、你在生产上遇到，排查方向会完全跑偏。「造了 A 却用了 B」这种错，Rust 的所有权系统平时帮你挡掉大半（unused variable 警告就是信号——warpped 没被使用，警告早就喊过了），但 job 本身是合法值，编译器无法知道你「意图」用哪个。

③ recv 补的解构行
let Inner { slot, wake } = &*self.inner;——你贴了操作步骤，但步骤里的两个名字凭空不存在。这行干的事：把 Arc<Inner<T>> 解一层引用（&*：* 穿透 Arc 智能指针，& 借住），再把两个成员的字段名借出来。从此 slot 是 &Mutex（锁本身），wake 是 &Condvar。你之前缺的就是这一步「把东西从结构体里拿出来」，所以编译器说 slot not found。

④ Drop 删 self.sent
你删了 sent 字段但忘了删引用它的代码。深层原因重申：槽的状态就是账本。Filled = 发过了，Empty = 没发。两本账必然漂移——今天忘了同步，三个月后就是线上 bug。

⑤ send 的写法里藏着一个联动
send(self, value) 结束后，self 被 drop → Sender 的 Drop 会执行。它看到槽是 Filled（不是 Empty），所以什么都不做。也就是说：正常发送的路径上，Drop 白跑一趟但无害；只有「没来得及发就死了」（panic、提前 drop）的路径，Drop 才把 Empty 改成 Closed、唤醒等待方报 Err。一个 Empty 判别同时伺候两条路径——这就是为什么不需要任何「防止 Drop 弄坏数据」的代码。
